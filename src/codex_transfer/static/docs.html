AUDITED SESSION OPERATIONS

理解 Session，再安全地改变它

Codex Transfer 管理本机及 Codex Desktop 当前连接主机上的 Session。它优先保留原始数据，所有写操作都经过预检、快照、审计和结果验证。

默认选择 Fork

Fork 创建独立 thread，原 Session 不变。只有明确需要改变原会话归属时才使用移动。

核心原理

Session 不是一段纯文本聊天。它由 rollout 事件流、SQLite 索引、项目与工作目录信息，以及模型后端产生的状态共同构成。Provider 迁移只改变“由谁接管下一次恢复”的路由信息，不会转换内部协议。

rollout JSONL+SQLite thread→预检与快照→Fork 或移动→哈希验证

Provider 标识不等于凭据

model_provider 是路由和列表分桶标识。API Key、OAuth、Base URL 与模型映射存在于独立配置中，Codex Transfer 从不复制或备份它们。

大列表按需读取

工作台首屏只读取 Session 摘要，超长标题会截断；将鼠标停在卡片上或点开详情后，才会读取完整标题。选择 Session 时只更新相关卡片和队列，不会重新创建整个网格。

PROVIDER MENTAL MODEL

Provider 是一条有名字的运行时路线

Provider 告诉 Codex 用什么协议、哪个地址和哪种认证方式发送下一次模型请求。它不是 Session、账号或密钥。Session 通常只记住 model_provider 这个 ID；具体定义、凭据和网络出口在恢复 Session 时才分别解析。

必须分清的四层

层次回答的问题迁移时是否复制
Provider IDSession 要引用哪个名字？Fork 或 Move 会设置它
Provider 定义这个名字对应什么协议和地址？不复制，目标主机独立配置
认证凭据谁有权调用这个服务？不复制、不备份
实际网络路线请求此刻最终去了哪里？运行时决定，可能随时间变化
ID 区分大小写

openai 与 OpenAI 可以是两个不同 Provider，指向完全不同的地址。跨主机存在同名 ID，也不代表两端配置、凭据或上游相同。

Codex 恢复 Session 时发生什么

  1. 1
    读取 Session

    从 rollout 与 SQLite 索引中取得 model_provider ID。

  2. 2
    合并定义

    加载内置 Provider，再按精确 ID 合并 [model_providers.*] 配置。

  3. 3
    解析认证和出口

    根据 Provider 定义、认证模式和显式 base_url 确定请求路线。

  4. 4
    发送请求并续写

    通过相应协议调用模型，随后把新事件写回 Session；历史仍主要保留 Provider ID。

内置与自定义

Codex 内置 openai Provider。未显式覆盖地址时，ChatGPT 登录与 API Key 登录会选择不同的官方出口。自定义 Provider 常用于企业网关、兼容 API 或本地切换代理。历史 Session 还可能保留一个已从配置删除的 ID：工作台能显示它，不代表它现在一定可以恢复。

model_provider = "company-gateway"

[model_providers.company-gateway]
name = "Company Gateway"
base_url = "https://gateway.example.com/v1"
wire_api = "responses"
requires_openai_auth = true

Codex Transfer 应怎样使用这个模型

Fork 或 Move 改变的是 Session 的 Provider 引用，不会把密钥和 Provider 配置一起带走。操作前应确认目标主机存在大小写完全一致的 ID、地址和协议符合预期、认证有效、模型别名与工具可用，并确认 Session 未被写锁占用。

工作台可直接检查路线

鼠标悬浮或键盘聚焦左侧 Provider、当前路线、目标 Provider 下拉框或预检路线，可以查看对应主机上的 Endpoint、协议、认证方式、能力、重试设置、已观察模型和 Session 数量。详情响应使用字段白名单，不包含凭据、Token、Header 值或查询参数值。

重要 Session 优先 Fork

先保留源 Session，在目标路线实际恢复并验证。Provider ID 只能证明记录过哪个名字，不能单独证明历史中每一轮实际使用的账号、上游或模型实现；混合 Provider 的逐轮来源也可能无法完整重建。

仓库参考文档：理解 Codex Provider。

存储模型

当前 Codex 同时在 rollout 的 session_meta.payload.model_provider 和 state_5.sqlite.threads.model_provider 中记录 Provider。移动必须协调修改两处；Fork 则交给 Codex app-server 创建完整的新 thread。

数据职责操作方式
rollout JSONL持久化事件、消息与推理状态移动时原子替换；Fork 由 Codex 创建
SQLite列表索引、Provider、项目和状态事务更新或由 app-server 写入
审计目录快照、Manifest、SHA-256 与事件链每次写操作创建新代际

Fork 到另一个 Provider

Fork 使用 Codex 官方 thread/fork interface，并传入目标 modelProvider。Codex 负责历史复制、lineage、新 thread ID、rollout 与索引写入，Codex Transfer 负责前后快照、风险确认和审计。

  1. 确认源 Session 未被写入。
  2. 备份源 rollout 与一致性 SQLite 快照。
  3. 启动同一 CODEX_HOME 的短生命周期 app-server。
  4. 调用 thread/fork，验证新 thread 的 Provider 与路径。
  5. 记录新 rollout 哈希；未发生变化前允许撤销。
批量 Fork 不是原子事务

多选后会逐条调用 thread/fork。每条都有独立备份和审计；中途失败时已完成的 Fork 会保留，剩余条目停止执行，需要在操作记录中逐条核对或恢复。

Fork 不是格式转换

它保留历史中的 encrypted_content。目标后端仍可能无法解密，但源 Session 不受影响。

移动原 Session

移动会在完整备份后原子改写 rollout Provider，并在 SQLite 事务中更新同一批 thread。任何一步失败都会尝试恢复迁移前快照。

移动适合需要让原 thread 出现在另一个 Provider 历史桶的场景。它的恢复条件更严格：迁移后只要 rollout 或数据库发生变化，自动恢复就会阻断。

远程与跨主机 Fork / Move

Codex Transfer 从本机进程树中识别由 Codex/ChatGPT Desktop 直接启动、命令包含 codex app-server proxy 的 SSH 连接。只把这些已打开且可免密登录的别名列入主机清单，不会扫描任意 SSH config。

来源和目标可以是同一台远程主机

同主机 Fork 直接调用官方 thread/fork。远程 Move 会验证目标 Provider 下的新 Session ID，再归档来源；不会通过 SSH 原地改写远程 SQLite。

  1. 从来源主机读取并检查 rollout、writer lock 与 SQLite 完整性。
  2. 在本机审计目录保存来源 rollout 和一致性数据库快照。
  3. 仅当主机不同时，把 rollout 暂存到目标 CODEX_HOME/imports/codex-transfer。
  4. 同主机调用 thread/fork，跨主机则调用实验性 thread/fork.path。
  5. 验证目标 Provider、rollout 和索引；Move 只有在全部验证成功后才归档来源。
凭据不会随 Session 传输

API Key、OAuth、Base URL、模型别名和 Provider 配置必须提前在目标主机独立设置。目标 Project 必须是目标主机上已经存在的绝对路径。

这是实验性 Codex 接口

thread/fork.path 可能随 Codex 版本变化。两端版本不兼容时预检或导入会失败；保留审计快照，先 Fork 验证，再考虑 Move。

归档与还原归档

Codex Transfer 在当前选择的本机或 Desktop SSH 主机上调用 Codex 官方 thread/archive 与 thread/unarchive。归档只改变默认列表中的可见状态，不删除聊天历史，也不改变 Provider；Codex 可能同时移动 rollout 并更新 SQLite 路径，因此每条操作仍会先把两者备份到本地审计目录。

  1. 关闭准备操作的 Codex 任务。
  2. 在 Session 卡片上点击归档或还原归档图标。
  3. 检查远程 writer lock、当前归档状态和数据库完整性。
  4. 输入 ARCHIVE 或 UNARCHIVE。
  5. 操作独立执行、验证并写入带主机 ID 的审计记录。
批量归档不是原子事务

中途失败时，已完成条目会保留，后续条目停止。每条都有独立快照，可以从操作记录定位恢复依据。

“占用”到底表示什么

Codex Transfer 检查 thread-writer-locks/<session-id>.lock，并尝试取得非阻塞独占锁。拿不到锁说明另一个 Codex 进程拥有独占写入权，此时所有修改都会被阻断。它可能正在运行，也可能只是已经加载。

当前 Codex 在恢复 Session 时取得 writer lock。关闭任务只会取消当前订阅；app-server 要等“没有订阅者且没有活动”同时持续 30 分钟，才卸载 recorder、发出 thread/closed 并释放锁。

不能安全强制抢占

删除 .lock 路径不会撤销旧进程持有的内核锁，反而可能让第二个 writer 锁住新 inode。thread/unsubscribe 也只能取消调用方自己的订阅。Codex Transfer 不删除活锁、不终止占用进程。

实时更新如何避免卡顿

本机使用原生 kqueue 文件事件和 SSE。锁目录变化只读取轻量锁快照；SQLite/WAL 连续写入会先静默合并，并且只有界面可见元数据变化时才刷新工作区，普通对话追加会被过滤。页面隐藏时暂停刷新，重新可见后只同步一次，不运行周期性全量轮询。

Desktop 的既有 SSH proxy 不会转发远端文件事件，因此远端主机在选择主机、窗口重新可见、手动刷新和 Codex Transfer 操作完成时刷新，避免常驻远端扫描。

备份、审计与恢复

操作 Manifest 记录输入 Session、目标 Provider、风险、文件路径、备份位置和前后哈希。审计 JSONL 使用前一事件哈希形成可检测篡改的链。

三种不同的恢复

字节恢复
把文件和数据库恢复为旧快照，可能丢弃后续变化。
功能恢复
Session 能继续运行，依赖凭据、模型和后端兼容性，无法保证。
来源恢复
重建每轮消息的 Provider 来源；trace 缺少可靠逐轮标记，无法自动完成。

风险模型

风险为什么发生Codex Transfer 的处理
加密推理不可移植后端生成不透明 encrypted_content计数并在确认时告警
目标凭据缺失Provider 标签不携带认证不接触密钥，要求独立配置
混合来源不可追溯没有可靠的逐轮 Provider 字段明确提示，禁止声称无损恢复
并发写入Codex 与 Codex Transfer 同时修改状态尝试非阻塞独占 writer lock，失败即阻断
恢复覆盖新聊天操作后状态已经分叉比较哈希并阻断自动恢复

安装与启动

./install.sh
codex-transfer

# 短命令
ct

安装器要求 Python 3.11+，创建隔离环境，并在 ~/.local/bin 提供两个命令。它不会覆盖同名普通文件，也不会删除旧名称下的备份。默认服务地址为 http://127.0.0.1:8765。

codex-transfer \
  --codex-home /path/to/.codex \
  --data-dir /private/backup/path \
  --codex-bin /path/to/codex \
  --port 8765

能力边界

  • Codex 本地存储和实验性 app-server 字段可能随版本变化，未知结构应当拒绝写入。
  • 只能发现本机 Desktop 当前打开的 SSH proxy；仅在远端启动的辅助进程无法反向暴露主机。
  • 跨主机操作创建新的目标 Session ID；它不会让 CLI 创建的 Session 自动归属到 Desktop 的远程 Project 元数据。
  • 哈希链可检测意外修改，但不是签名，拥有文件写权限的攻击者可以重写日志与备份。
  • 备份包含完整聊天和工具输出，应存放在私密磁盘并纳入用户自己的保留策略。
