AUDITED SESSION OPERATIONS

Understand a session before changing it

Codex Transfer manages sessions on the local machine and on hosts currently connected by Codex Desktop. Every write is preceded by preflight checks and snapshots, then followed by audit logging and result verification.

Prefer a fork

A fork creates an independent thread and leaves the source untouched. Move only when the original session itself must change ownership.

Core concepts

A session is not plain chat text. It combines a rollout event stream, a SQLite index, project and working-directory metadata, and state created by the model backend. A provider transfer changes who handles the next resume; it does not convert the protocol or historical payloads.

rollout JSONL+SQLite thread→preflight + snapshot→fork or move→hash verification

A provider ID is not a credential

model_provider is a routing and grouping identifier. API keys, OAuth state, base URLs, and model mappings live in separate configuration. Codex Transfer never copies or backs them up.

Large lists load on demand

The first view reads compact session summaries. Full long titles load only when details are opened, and selecting a session updates the relevant card and queue instead of rebuilding the entire grid.

PROVIDER MENTAL MODEL

A provider is a named runtime route

A provider tells Codex which protocol, endpoint, and authentication mode to use for the next model request. It is not a session, account, or secret. Sessions normally retain only a model_provider ID; the definition, credential, and network path are resolved separately when the session resumes.

The four layers

LayerQuestion answeredCopied during transfer?
Provider IDWhich name does the session reference?Fork or move sets it
Provider definitionWhich protocol and address does that name mean?No; configured independently
CredentialWho may call the service?Never copied or backed up
Network routeWhere does the request ultimately go now?Resolved at runtime
IDs are case-sensitive

openai and OpenAI can be separate providers with different endpoints. Matching IDs on two hosts do not prove matching configuration, credentials, or upstream services.

What happens when Codex resumes a session

  1. 1
    Read the session

    Obtain the model_provider ID from the rollout and SQLite index.

  2. 2
    Merge definitions

    Load built-in providers and merge [model_providers.*] configuration by exact ID.

  3. 3
    Resolve auth and egress

    Use the definition, auth mode, and explicit base_url to determine the request route.

  4. 4
    Request and append

    Call the model through the selected protocol and append new events; history still primarily records the provider ID.

Built-in and custom providers

Codex includes an openai provider. ChatGPT login and API-key login can select different official endpoints when no URL is overridden. Custom providers commonly represent company gateways, compatible APIs, or local switching proxies. A historical session may also reference an ID that has since been removed from configuration.

model_provider = "company-gateway"

[model_providers.company-gateway]
name = "Company Gateway"
base_url = "https://gateway.example.com/v1"
wire_api = "responses"
requires_openai_auth = true

How Codex Transfer applies this model

Fork and move change the session's provider reference. They do not carry secrets or provider configuration. Before operating, verify the exact case-sensitive ID, endpoint, protocol, authentication, model aliases, tool availability, and writer-lock state on the destination host.

Inspect routes in the workspace

Hover or focus a provider, current route, target selector, or preflight route to see endpoint, protocol, auth mode, capabilities, retry policy, observed models, and session counts. The response uses a field allowlist and contains no credentials, tokens, header values, or query parameter values.

Fork important sessions first

Validate the actual target route while preserving the source. A provider ID alone cannot prove which account, upstream, or model implementation produced each historical turn, especially in a mixed-provider trace.

Repository reference: Understanding Codex Providers.

Storage model

Current Codex versions record the provider in both rollout session_meta.payload.model_provider and state_5.sqlite.threads.model_provider. A move coordinates both locations. A fork delegates creation of a complete new thread to Codex app-server.

DataResponsibilityOperation
rollout JSONLEvents, messages, and reasoning stateAtomic replacement for move; Codex creates forks
SQLiteList index, provider, project, and stateTransaction update or app-server write
Audit directorySnapshots, manifest, SHA-256, and event chainNew generation for every write

Fork to another provider

Fork calls the official Codex thread/fork interface with a target modelProvider. Codex owns history copying, lineage, the new thread ID, rollout, and index writes. Codex Transfer owns preflight, snapshots, risk confirmation, and auditing.

  1. Confirm the source session has no writer.
  2. Back up its rollout and a consistent SQLite snapshot.
  3. Start a short-lived app-server for the same CODEX_HOME.
  4. Call thread/fork and verify the new thread, provider, and path.
  5. Record the new rollout hash so an unchanged fork can be removed during recovery.
Batch forks are not atomic

Selected sessions are forked one at a time, each with an independent backup and audit entry. Completed forks remain if a later item fails.

A fork is not a format conversion

Historical encrypted_content remains intact and may not be decryptable by the target backend. The source session is unaffected.

Move the original session

After a complete backup, move atomically rewrites the rollout provider and updates the corresponding SQLite threads in a transaction. Failures trigger an attempt to restore the pre-move snapshot.

Move is appropriate when the original thread must appear under another provider. Recovery is strict: any post-move rollout or database change blocks automatic restoration.

Remote and cross-host fork and move

Codex Transfer discovers SSH connections launched directly by Codex or ChatGPT Desktop whose command includes codex app-server proxy. Only currently open aliases with key-based login are listed; arbitrary SSH configuration is not scanned.

The source and target may be the same remote host

A same-host Fork calls official thread/fork directly. Remote Move verifies the new target-provider Session ID and then archives the source; it does not rewrite remote SQLite over SSH.

  1. Inspect the source rollout, writer lock, and SQLite integrity.
  2. Store the source rollout and consistent database snapshots in the local audit directory.
  3. When hosts differ, stage the rollout under target CODEX_HOME/imports/codex-transfer.
  4. Use direct thread/fork on the same host, or experimental thread/fork.path across hosts.
  5. Verify provider, rollout, and index. A move archives the source only after full target verification.
Credentials do not travel with sessions

Configure API keys, OAuth, base URLs, model aliases, and provider definitions independently on the target. The target project must already exist as an absolute path on that host.

This uses an experimental Codex interface

thread/fork.path can change between Codex versions. Keep the snapshot, test a fork first, and only then consider moving the source.

Archive and unarchive

On the selected local or Desktop SSH host, Codex Transfer calls official thread/archive and thread/unarchive. Archive changes default-list visibility; it does not delete chat history or change the provider. Because Codex may move the rollout and update its SQLite path, both are backed up for every item.

  1. Close the Codex task you intend to change.
  2. Use the archive or unarchive control on its card.
  3. Check writer locks, archive state, and database integrity.
  4. Enter ARCHIVE or UNARCHIVE.
  5. Execute, verify, and audit each session independently.
Batch archive is not atomic

Completed items remain if a later item fails. Each item has an independent snapshot and audit record.

What “In use” means

Codex Transfer attempts a non-blocking exclusive lock on thread-writer-locks/<session-id>.lock. Failure means another Codex process owns the exclusive writer. It may be actively running or merely loaded.

Closing a task removes the current subscription, but app-server unloads the recorder, emits thread/closed, and releases the lock only after the thread has had no subscribers and no activity for 30 continuous minutes.

Forced takeover is unsafe

Deleting the .lock path does not revoke the kernel lock on the old inode and could let a second writer lock a new inode. thread/unsubscribe can only remove the caller's own subscription. Codex Transfer neither deletes live locks nor terminates their processes.

Live updates without polling

The local host uses native kqueue file events and SSE. Lock changes read only a lightweight snapshot. Bursts of SQLite/WAL writes are coalesced, and ordinary chat appends are filtered unless visible workspace metadata changed. Hidden pages pause refresh and synchronize once when visible again.

Existing Desktop SSH proxies do not forward remote file events. Remote hosts refresh on host selection, visibility return, explicit refresh, and completion of a Codex Transfer operation, avoiding permanent remote scans.

Backup, audit, and recovery

The operation manifest records input sessions, target provider, risks, file paths, backup locations, and before/after hashes. Audit JSONL links each event to the previous event hash so accidental modification can be detected.

Three meanings of recovery

Byte recovery
Restore files and database rows to an old snapshot, potentially discarding later changes.
Functional recovery
Resume the session successfully; this depends on credentials, models, and backend compatibility and cannot be guaranteed.
Provenance recovery
Reconstruct the provider used for every turn; traces do not reliably retain this information, so it cannot be automated completely.

Install and run

./install.sh
codex-transfer

# Short alias
ct

The installer requires Python 3.11+, creates an isolated environment, and provides both commands under ~/.local/bin. It does not overwrite a regular file with the same name. The default service address is http://127.0.0.1:8765.

codex-transfer \
  --codex-home /path/to/.codex \
  --data-dir /private/backup/path \
  --codex-bin /path/to/codex \
  --port 8765

Limitations

  • Codex local storage and experimental app-server fields can change between releases; unknown structures must be rejected.
  • Only SSH proxies currently opened by local Desktop can be discovered. A relay launched only on a remote host cannot expose that host back to this tool.
  • Cross-host transfer creates a new target Session ID; it does not automatically attach a CLI-created session to Desktop remote-project metadata.
  • The hash chain detects accidental modification but is not a signature. An attacker with filesystem write access can rewrite logs and backups.
  • Backups contain complete chats and tool output. Keep them on private storage and apply your own retention policy.
